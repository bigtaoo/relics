# 10 · 战斗逻辑性能（召唤流 300 单位）

> 状态：原型实测（2026-10-07）。三战规则还没还原（02），这里用的是一套代替规则的压测原型，回答两个问题：**服务器一核能跑多少局**，**手机上算一场 300 单位的战斗要多久**。
> 结论先行：服务器不是问题；手机端的战斗核心不能留在热更解释器里跑召唤流。**已决定把 Core 编进壳（方案 A，ADR-010）**，以后可升级到 DHE（方案 B）。

## 1. 压测原型

代码在 `src/Battle.Core/Sim/`（`CrowdBattle`），和正式核心遵守同样的确定性规则：只用 `FP` 和注入的 `Prng`，按 id 顺序遍历，运算全部 checked。

- 30 Hz，最长 900 tick（30 秒战斗）。即时制自动战斗，每个单位每 tick 都要做：buff 结算 → 召唤 → 索敌（每 0.5 秒重新找最近的敌人）→ 进入射程就普攻，否则移动并和周围单位互相推开。
- 普攻：暴击（每次都抽随机数）、减伤、蓝量；满蓝放技能：范围伤害、灼烧、眩晕、给最残的 3 个友军加盾、治疗，并给自己叠攻击 buff。
- 每方 8 个英雄（2 坦克、2 战士、2 弓手、2 辅助）。召唤流时 4 个英雄是召唤师，持续补召唤物到上限。
- 空间网格：每 tick 开始按格子做计数排序，索敌和推挤只看附近的格子。
- 输出事件流（演出层消费，03 §8）和终局哈希（客户端上报，01 §6）。

| 场景 | 内容 | 平均同屏 / 峰值 |
|---|---|---|
| duel16 | 8 对 8，无召唤 | 10 / 16 |
| summon300 | 双方召唤流，召唤物死了马上补，一直维持在上限附近 | 248 / 300 |
| crowd300 | 开局就是 300 单位，召唤师补位 | 175 / 300 |
| crowd500 | 开局 500 单位 | 263 / 500 |

规则写得比较笨（每个单位每 tick 都做完整流程，召唤物死了就补），算出来的开销应该**高于**真实规则。三演本身是回合制，真实规则大概率更便宜。

## 2. 实测数据（开发本 Core Ultra 7 165H）

| 运行环境 | duel16 一场 | summon300 一场 | 每 tick 平均 / 最坏 | 说明 |
|---|---|---|---|---|
| .NET 10（服务端） | 1.9 ms | **97 ms** | 0.11 / 1.3 ms | `tools/SimBench` |
| IL2CPP 原生（Core 编进壳里） | 1 ms | **226 ms** | 0.25 / 3.5 ms | 临时把 Core 移出热更列表打的正式版包 |
| HybridCLR 解释器（现状，正式版） | 13 ms | **2772 ms** | 3.1 / 7.7 ms | `Relics.exe -simbench` |
| HybridCLR 解释器（开发版） | 15 ms | 3154 ms | 3.5 / 9.7 ms | 开发版只慢约 12% |

- **确定性**：同一个种子，.NET、IL2CPP 原生、HybridCLR 解释器三种环境的终局哈希完全一致。哈希锁在 `CrowdBattleTests.GoldenHash`，手机上跑 `-simbench` 会逐项对照。
- 解释器比 IL2CPP 原生慢 **12 倍**，比 .NET 慢约 28 倍。
- 空间网格很关键：不用网格（每次都扫全部单位）时 summon300 要 217 ms（.NET），慢 4 倍。
- 服务端不记录事件时，每场分配约 0.6 MB，记录事件约 1.3 MB。GC 压力不大。

## 3. 推算

### 服务器

- summon300 单线程每秒 19 场。一局 8 人每轮 4 场战斗，一轮 50 秒（准备 20 + 战斗 30），**就算每场都是召唤流，一核也能跑约 240 局**。22 线程的开发本全开约 2500 局（小核和超线程只有约一半效率）。
- 普通 8 对 8 每场 2 ms，一核能跑几千局。
- 结论：战斗逻辑的 CPU 在服务器成本里可以忽略，成本主要会在网络、带宽和运维上。

### 手机

A16 的大核单核大约是开发本大核的 1/3～1/4（推算，真机待测）；iPhone 13 和开发本差不多。

| 环境 | summon300 一场（A16 推算） | 每 tick 平均 | 30 tick/秒占用一个核的比例 |
|---|---|---|---|
| 解释器（现状） | 约 10 秒 | 约 11 ms | 约 33% |
| IL2CPP 原生 | 约 0.8 秒 | 约 0.9 ms | 约 3% |

影响：
- **观战快进**（01 §4）：战斗快结束时切去看别人，要从头算到当前 tick。解释器下要算约 10 秒，没法接受；原生约 0.8 秒，还要再想办法（见下）。07 §6 定的目标是 100 ms 以内，普通 8 对 8 在解释器下也能达标（PC 13 ms，A16 推算约 50 ms），召唤流不行。
- **自己的战斗**：边播边算的话，解释器每帧要多花约 11 ms，30 fps 的帧预算一共才 33 ms。
- 发热：解释器多烧 10 倍 CPU，召唤流对局会明显更烫。

## 4. 方案（2026-10-07 定为 A，见 ADR-010）

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A. Core 编进壳** | `Automatic.Battle.Core` 移出热更列表，IL2CPP 原生编译；数值和战法改成数据，走资源热更 | 快 12 倍，壳里只多一个程序集 | 改 Core 的代码要发新壳（商店审核）。`EngineVersion` 匹配校验本来就有（07 §5），老壳的玩家要强制更新 |
| B. HybridCLR 旗舰版 DHE | Core 原生编译进壳；热更时工具自动比对，没改过的函数照样跑原生，只有改过的函数走解释器 | 速度和 A 一样（不改时就是原生），Core 代码仍可热更：大版本全原生，紧急修复只有改到的函数变慢 | 商业授权，要发邮件询价；多一个供应商依赖；每个发布过的壳的 AOT dll 都要存档（生成差异文件用，07 §4 本来就要存） |
| C. 优化解释执行 | 降 tick 率（30 → 15 Hz 直接减半）、减少 FP 运算符调用、热点手写 | 不改架构 | 估计最多快 2～4 倍，离原生还差很远 |
| D. 不在客户端从头算 | 观战时服务端下发当前 tick 的状态快照，客户端只往后算；战斗在后台线程预算 | 快进成本和战斗长度无关 | 协议多一种消息（快照）；和 A、B 不冲突，可以叠加 |

HybridCLR 的版本（官网 2026-10 查到的说法）：
- 社区版：免费，纯解释执行。我们现在用的就是社区版（8.15.0），上面 §2 测的就是它。
- 专业版：数值类指令的解释执行性能是社区版的 280%～735%。
- 旗舰版：在专业版基础上加 DHE。官网说没改动的代码性能与原生完全相同，比纯解释快 3～30 倍以上。
- 价格都要发邮件询价（business@code-philosophy.com），按一个项目、含两年支持计。

§2 已经验证过：同一份 Core 在原生和解释器下结果逐位一致，所以 DHE 下一部分函数跑原生、一部分跑解释器，不会影响确定性。

商业版没有试用，要用公司邮箱询价、签约后才提供代码，所以先做 A。

当时的建议是 **A 或 B，再加 D**：Core 原生编译，解决每 tick 的开销和发热。A 和 B 的代码结构完全一样，区别只在打包配置和授权，所以可以先按 A 开发，上线前再决定要不要买 B；召唤流的观战快进再用快照或后台线程兜底，因为原生下仍要约 0.8 秒。
A 改了 ADR-008 中「Battle.Core 放在热更层」一条。数据驱动本来就是 03 的目标（换皮只改数据），战法数据放进单独的热更程序集（03 §7），平时的数值调整仍然只发热更。D 等写观战时再做。

### A 的落地（2026-10-07）

- `BootConfig.HotUpdateAssemblies` 只剩 `Automatic.Game`；Core 加进补充元数据列表（`AotMetadataAssemblies`），热更代码可以实例化它的泛型（如 `Prng.Shuffle<T>`）。
- `Assets/Boot/link.xml` 整体保留 Core：壳里只有热更代码调用 Core，不保留的话，打壳时没用到的部分会被裁掉，下一次热更就调不到了。
- 打壳时记下 `src/Battle.Core` 源码的哈希（`HybridCLRData/ShellCore/{平台}.txt`），构建热更时对比，Core 改了就拒绝发布（`ShellCore`）。
- PC 开发版实测：summon300 一场 218 ms（解释器开发版 3154 ms），crowd300 107 ms，三项哈希 PASS；`-hotcheck` 7 项黄金值全部 PASS，包括热更代码调用 Core 的泛型 `Shuffle<int>`。临时改一行 Core 再构建热更，被拒绝，CDN 版本不变。
- 安卓：现有 APK 的 Core 还是热更的，手机到了要先重新打 APK（`android.sh --install`）。

## 5. 复现

```bash
dotnet run -c Release --project tools/SimBench            # 服务端：各场景耗时、确定性、单核和全核吞吐
artifacts/player/PC/Relics.exe -simbench -seeds 3 -batchmode -nographics -logFile sim.log
tools/bench/android.sh sim                                 # 安卓真机（要用 Core 编进壳之后打的 APK）
```

正式版（非开发版）的包：`unity run client ... -executeMethod Automatic.Editor.Batch.BuildPlayer -release`，输出到 `artifacts/player/PC-release`。
现在的包里 Core 就是原生的。要重测解释器，临时把 `Automatic.Battle.Core` 加回 `BootConfig.HotUpdateAssemblies`（排在 `Automatic.Game` 前面）并从 `AotMetadataAssemblies` 去掉，跑 `Setup` 同步 HybridCLR 设置，打完改回来。

## 6. 待做

- 真机：A16 跑 `android.sh sim`，iPhone 13 等 iOS 流水线。
- 三战规则还原后，用真实规则重测一次。如果是回合制，开销会低很多。
- 原型里有两个顺序问题，写正式核心时要避免：
  - 固定的行动顺序会让后手方先打到人：后手方等对面走进射程再出手，而偶数攻击间隔让单位永远落在同一种奇偶的 tick 上，所以按 tick 轮换先手也没用。现在每 tick 抽一次随机数决定哪一方先动。
  - 推挤逐个叠加时，结果依赖网格的遍历顺序，结果是高 y 一侧总赢。现在把所有推力从同一点算出再求和，与顺序无关。
