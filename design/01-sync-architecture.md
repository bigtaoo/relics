# 01 · 同步架构

> 决策：ADR-004；网络与消息格式见 ADR-013。状态：草案；最小闭环已实现（§8）。

## 1. 总览

| 阶段 | 有无输入 | 同步方式 | 权威方 |
|---|---|---|---|
| 准备 | 有（买、卖、刷新、布阵、升级、延长卡） | 指令 + 结果下发 | 服务端 |
| 战斗 | 无 | 确定性模拟：快照 + 种子 + 开始时刻 | 服务端算出的结果为准，客户端本地同样算一遍用于演出 |

服务端进程沿用 funny / daydayup 的划分：网关（登录、票据）/ 匹配服 / 对局服。对局服内部运行 `Battle.Core`。

## 2. 准备阶段

- 客户端发送带序号的指令，服务端校验后回复结果，并把公开信息广播给所有人，例如阵容变化（三演允许查看他人阵容）。
- **商店内容、卡池余量、随机种子永远不下发**。客户端只收到「你这次刷新出的 5 张牌」。
- 截止时刻以服务端时钟为准。有人使用延长卡时，服务端广播新的截止时刻。
- 截止时刻一到，服务端冻结所有人的阵容快照，进入战斗阶段。

## 3. 战斗时间轴（观战同步的基础）

### 3.1 一切时长都在逻辑里

- 战斗按固定 tick 推进，**10 Hz**（ADR-014：三战是回合制，0.1 秒的精度足够，开销只有 30 Hz 的三分之一）。
- **每个行动、每次阶段切换占用多少 tick，由 Core 中的数据表决定**，现行的表是 `TurnTiming`：普攻 16 tick（第 7 tick 命中）、战法 27 tick（第 9 tick 命中）、牌型发动 25 tick、行动间隔 2 tick。
  - 演出层的动画和特效必须塞进这段时长里，不能反过来让逻辑等动画播完。
- 因此一场战斗的总 tick 数在开战瞬间就确定了，「第 t 秒在演哪一步」对所有人完全一致。
- 想在终极阵容成型时做慢放演出，必须作为逻辑中的「演出停顿 tick」写进时间轴，不能只在客户端本地放慢。否则观战者之间会出现进度差。

### 3.2 开战广播

战斗开始时（服务端时刻 T0），服务端向每个客户端下发：

```
BattleRound {
  round, t0ServerMs, maxTicks,
  battles: [ { battleId, sideA: Snapshot, sideB: Snapshot, seed } ... ]  // 本轮所有对战
}
```

- 种子在 T0 时刻才生成，之前任何人都无从得知。
- 奇数人数时的幽灵对手（ghost）也是一个普通的 battle 条目，处理方式相同。
- 实现（`src/Net/Proto/match.proto`）里 `BattleRound` 还带 `tickHz` 和本轮结束时刻 `endsMs`。T0 取冻结时刻之后 200 ms，让消息先到、客户端从第 0 tick 正常开始，而不是一上来就快进。

### 3.3 时钟

- 客户端与服务端做时钟偏移同步（类似 NTP：多次往返取延迟最小的那次），误差控制在几十毫秒内。
- 任何客户端在任意时刻都可以算出：`当前 tick = (服务端当前时刻 − T0) × 10`。

## 4. 观战（回答「我的战斗已经结束，去看别人的会不会不同步」）

1. 切换到另一场战斗时，客户端用这场战斗的快照和种子，**无演出地快进模拟**到当前 tick，然后从这一 tick 开始播放演出。普通 8 对 8 只需几毫秒；召唤流 300 单位在热更解释器里要几秒，原生也要约 1 秒（手机推算），需要快照或后台线程兜底，见 10。
2. 所有观看同一场战斗的人看到的都是同一 tick，误差只有时钟偏移的几十毫秒。来回切换不会累积误差，因为每次切换都重新按服务端时钟对齐。
3. 自己的战斗提前结束时，可以自由切换观看他人的战斗。每一轮的结束时刻固定为 `T0 + 战斗时长上限`，与谁先打完无关。
4. **战斗必须有硬上限**：决战回合数达到上限时，按剩余兵力等规则判定胜负，具体以三战规则为准（见 02）。这样保证 `maxTicks` 在本轮的战斗时长之内。
5. **结果揭晓时机**：扣血、名次变化在该场战斗的结束 tick 才显示，不在 T0 显示。

### 已知且接受的信息泄露

- 客户端在 T0 就拿到了所有对战的快照和种子，被改过的客户端可以立刻算出本轮所有战斗的结果，比正常显示早最多 30 秒。
- 影响很小：战斗中没有任何可做的决策，下一轮的商店也要到准备阶段才下发。对手阵容本来就是公开的。
- 如果以后需要收紧：只下发自己那场战斗；观战时再按需请求，服务端在当前 tick 之前不给结果。代价是切换观战时多一次往返请求。

## 5. 断线重连 / 中途加入

- 入座时服务端发一个重连令牌（`Welcome.resumeToken`）。客户端断线后建一条新连接，在 `Join` 里带上令牌即可回到原座位；同一座位只保留最新的连接。令牌对不上就拒绝并断开。
- 重新连上后，服务端一次性下发 `MatchState`，内容是：
  - 当前阶段、回合、阶段截止时刻；
  - 所有人的公开信息（血量、阵容、在线状态、名次）；
  - 自己的准备状态（商店、金币、阵容）；
  - 战斗阶段还附带本轮的 `BattleRound`。
- 战斗阶段沿用观战逻辑：快进到当前 tick 后继续播放，结束时照常上报哈希。
  - 实测：8 人局第 2 回合中途断线，300 ms 后重连，快进约 400 tick（4 场 8 对 8），用时约 7 ms。
- **掉线期间的准备阶段：阵容保持不变，不托管**。
  - 收入照常发放，商店照常刷新但没人买；战斗照常用冻结时的阵容参加。
  - 理由：
    - 和三战、云顶一致，玩家能预期；
    - 断线大多只有几秒，托管 AI 做出的买卖反而可能违背玩家意图；
    - 服务端少一套要维护的逻辑。
  - 长时间断线（例如连续几回合）要不要接入托管 AI，等有了真实断线数据再定（§7）。
- 不需要像 funny 那样重放整局的帧日志，所以重连成本很低。

## 6. 一致性校验

- 客户端在战斗结束时上报状态哈希。哈希与服务端不一致时记录日志并上报，**结果始终以服务端为准**，不需要 funny 的空闲客户端仲裁机制。
  - 实现：客户端模拟本轮全部战斗（不只自己那场），每场结束时上报 `哈希 + 结束 tick`，服务端逐场比对并计数（一致 / 不一致 / 缺报）。`RoundResult` 带回服务端的每场结果，客户端也拿自己的哈希比一遍。
- 黄金回放测试：固定若干组「快照 + 种子 → 最终哈希」，任何改变战斗结果的改动都必须升 `EngineVersion` 并更新这些期望值。
- 编译期检查（ADR-012）：分析器 `src/Battle.Core.Analyzers` 在 Battle.Core 里把不确定的写法报成编译错误，dotnet 和 Unity 都生效：

  | 规则 | 禁止 |
  |---|---|
  | DET001 | `float` / `double` / `decimal`：类型、字面量、隐式转换成浮点传给框架方法 |
  | DET002 | `System.Math`、`MathF` |
  | DET003 | `DateTime`、`DateTimeOffset`、`TimeZoneInfo`、`Environment`、`Stopwatch` |
  | DET004 | `System.Random`、`RandomNumberGenerator` |
  | DET005 | `Guid` |
  | DET006 | `System.Threading*`、`System.Timers`、`async` / `await`、`lock`、`volatile` |
  | DET007 | 遍历 `Dictionary` / `HashSet` 及其 `Keys` / `Values`、`IDictionary`、`ISet`、并发和不可变的字典与集合：`foreach`、LINQ、传给 `List` 构造或 `string.Join`、`GetEnumerator`、`CopyTo`。`SortedDictionary` / `SortedSet` 可以 |
  | DET008 | `object` / `ValueType` / `string` 的 `GetHashCode`、带字符串参数的 `GetHashCode`（`StringComparer`）、`System.HashCode` |
  | DET009 | `[DeterminismExempt]` 没写理由 |

  - 所有规则都是错误且不可配置，`#pragma warning disable`、`NoWarn`、`.editorconfig` 都压不掉。
  - 唯一的例外方式是在外层成员、局部函数或类型上加 `[DeterminismExempt("理由")]`。每个豁免都要列在下面，`DeterminismTests.ExemptionsAreTheReviewedList` 会对照检查。
  - 当前豁免：无。

## 8. 最小闭环（2026-10-18 实现）

一局 8 人对局的完整流程已经能跑：大厅 → 准备 → 战斗 → 结算 → 下一回合 → 决出名次。

| 部分 | 位置 | 内容 |
|---|---|---|
| 协议 | `src/Net/Proto/match.proto` | 客户端 → 服务端：`Join`、`Command`（买、刷新、移动）、`BattleReport`、`Ping`；服务端 → 客户端：`Welcome`、`MatchState`、`PrepStart`、`PlayerState`、`CommandResult`、`PublicBoard`、`BattleRound`、`RoundResult`、`MatchEnd`、`Pong` |
| 客户端共用代码 | `src/Net`（Unity 包 `com.automatic.net`） | `MatchConnection`（WebSocket）、`ClockSync`（取往返最短的一次）、`MatchSession`（应用消息、按服务端时钟推进本轮全部战斗、上报哈希、带令牌重连）、`RoundSim`、`BattleFactory`（快照 → 战斗） |
| 服务端 | `src/Server` | Kestrel `/match`；`Match` 单线程循环处理输入和阶段截止，不用锁 |
| 机器人 | `src/Bot` | 用和游戏客户端相同的 `MatchSession`，准备阶段随机买、刷新、移动；可在指定回合的战斗中途断线再重连 |
| 测试 | `tests/Match.Tests` | 本机真实 WebSocket 跑完整一局：8 个机器人，其中 1 个在第 2 回合战斗中途断线重连。断言所有哈希一致、无缺报、重连后确实快进过 |

- **准备阶段是占位规则**，等真正的经济系统：
  - 棋盘固定 8 个槽位，对应核心原型里每边 8 个英雄。
  - 商店的每个选项指向一个槽位，买下就让这个棋子升一星，花费是当前星级 + 1。
  - 星级缩放生命和攻击：0 星 70%，1 星 100%，2 星 180%，3 星 320%。
  - 位置是半场 7×4 的格子，后排在第 0 行。
  - 收入：每回合 5，加上利息每 10 金币 1，最多 3。
  - 扣血：输家扣 2 + 回合数，平局双方各扣 1，打幽灵不扣血。
- **`BattleFactory` 是确定性输入的一部分**：核心原型还不接受阵容，现在的做法是先按 `Duel16` 建出战斗，再改单位的属性和位置。核心支持阵容输入后，这部分搬进核心。

**实测**（本机 loopback，Release，30 Hz，每回合 4 场 8 对 8，准备 5 秒）：

| 项 | 数值 |
|---|---|
| 下行，每客户端每回合 | 约 5.1–5.2 KB；断线重连的那一回合约 6.6 KB |
| 其中 `BattleRound` | 约 650 B（4 场的阵容和种子）。其余大部分是 `PublicBoard`：每条成功的指令都向全员广播一次阵容 |
| 上行，每客户端每回合 | 约 230 B |
| 服务端模拟本轮 4 场 | 3–13 ms（随 JIT 分层编译逐回合下降） |
| 服务端对局循环忙碌时间 | 每回合 5–38 ms |
| 服务端进程 CPU | 每回合 90–220 ms（含 Kestrel、8 条连接、心跳、GC）；第 1 回合含启动和 JIT，约 1.1 s |
| 断线重连快进 | 30 Hz 下 +110 tick，0.4 ms；测试里 900 Hz 时间轴下 +418 tick，约 7 ms（Debug） |
| 哈希 | 4 回合 128 次上报，全部一致；测试 5 回合 160 次，全部一致 |

- 按这些数，带宽不是问题：一局 30 回合，每个客户端下行不到 200 KB。
- 服务端 CPU 主要花在框架开销上，不在模拟上。召唤流 300 单位的模拟开销见 10 §3。
