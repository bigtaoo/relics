# 架构决策记录（ADR）

格式：编号 · 日期 · 结论 / 理由 / 影响。被推翻的决策不删，标注「已被 ADR-xxx 取代」。

## ADR-001 · 2026-10-05 · Unity 客户端 + C# 服务端 + 共享战斗核心

- **结论**：客户端 Unity 6（URP），服务端 .NET 10。战斗逻辑只有一份：`src/Battle.Core`（netstandard2.1 / C# 9），服务端用 ProjectReference 引用，Unity 当作本地 UPM 包引用。
- **理由**：funny 的教训是客户端、服务端各写一份逻辑会不同步。同一份 C# 源码同时跑在两端，从结构上消除这个问题。
- **影响**：Core 只能使用 C# 9 语法，不能引用 UnityEngine。构建输出放到 `/artifacts`，防止 Unity 导入 bin/obj。

## ADR-002 · 2026-10-05 · 定点数 `FP`：64 位整数，缩放 10000

- **结论**：`readonly struct FP`，内部存 `long Raw`，Scale = 10000。
  - 只能通过命名工厂构造：`FromInt` / `FromRatio` / `FromPercent` / `FromRaw`。
  - 没有任何隐式类型转换。
  - 乘除向零截断，运算全部 checked（溢出抛异常）。
- **理由**：
  - 三战的数值以百分比为主（如 125%、35.5%），四位小数足够，也便于人读。
  - 用 struct 加上不提供隐式转换，可以在编译期杜绝 funny ADR-065 那类「原始值和缩放值混用、差 1000 倍」的错误。
  - 回合制战斗不需要三角函数和开方。
- **影响**：伤害取整规则需要等截图还原后在 02 中确认，再在 Core 中实现。

## ADR-003 · 2026-10-05 · Prng 移植 daydayup v78（LCG + Murmur3 混合）

- **结论**：逐位移植 daydayup 的 prng，测试锁定与 TS 版逐位一致。按用途分别注入实例，不设全局随机。
- **理由**：daydayup 已经验证过这个生成器，修复了低位循环、近邻种子相关、洗牌覆盖不全等问题。
- **影响**：每新增一条随机流都要升引擎版本。

## ADR-004 · 2026-10-05 · 混合同步：准备阶段服务端权威，战斗阶段确定性同步

- **结论**：
  - 准备阶段：商店、卡池、经济只在服务端计算，客户端只发指令。
  - 战斗阶段：服务端下发阵容快照和本场新生成的种子，服务端和所有客户端用同一份定点数核心按固定 tick 推进。服务端的结果是权威结果。
- **理由**：自走棋如果全程帧同步，客户端会持有卡池和商店种子，可以预知以后的刷新（属于信息作弊，哈希校验抓不到，daydayup design/15 已有记录）。战斗阶段没有玩家输入，确定性同步只需要一次性下发输入。
- **影响**：
  - 观战、重连、回放只需要「快照 + 种子 + 开始时刻」。
  - 详细设计见 01。

## ADR-005 · 2026-10-05 · 3D 表现

- **结论**：角色和棋盘做 3D，Unity URP。
- **理由**：市场竞争激烈，表现力是差异化的必要条件（三演玩家的主要差评就是「演出弱」）。
- **影响**：美术成本和管线见 04。原型阶段先用占位模型，不让美术阻塞玩法验证。

## ADR-006 · 2026-10-05 · 第一阶段完整复制三战「三国演弈」

- **结论**：第一阶段完整复制规则、战法、数值，作为内部验证的基线；之后再优化，上线前全部替换为自有设计。
- **理由**：先拿到一个已被验证可玩的基线，再在这个基线上做改动，每项改动的效果都能对照出来。
- **影响**：
  - 三战原名只允许出现在内部数据和设计文档中，不能进入任何对外构建。
  - 每个武将都要标注「定位意图」，方便日后映射到自有角色（见 02）。

## ADR-007 · 2026-10-05 · 语言约定

- **结论**：设计文档用中文；代码、注释、提交信息用英文（由 hook 强制）。

## ADR-008 · 2026-10-06 · 客户端热更：HybridCLR + YooAsset

- **结论**：代码热更用 HybridCLR，资源热更用 YooAsset。热更 DLL 作为资源打进包，和美术资源走同一套版本清单与下载流程。
- **理由**：
  - HybridCLR 让热更代码就是普通 C#，与 IL2CPP 共存，支持 Unity 6 全部 LTS。不需要 Lua 或 ILRuntime 那样的第二套语言和绑定层，Battle.Core 也能原样参与热更。
  - YooAsset 的版本清单、增量下载、缓存校验开箱即用，与 HybridCLR 搭配是国内常见组合，坑基本都被踩过。
- **影响**：
  - 客户端分为 AOT 壳和热更层两层，详见 07。
  - ~~Battle.Core 放在热更层~~（2026-10-07 由 ADR-010 改为编进壳）。客户端与服务端的核心版本仍必须一致：匹配前强制校验 `EngineVersion` 和数据哈希。
  - 锁定 Unity 小版本，升级前先确认 HybridCLR 已支持。
  - iOS 上架存在下载可执行代码的合规风险，处理方式见 07 §8。

## ADR-009 · 2026-10-06 · 平台：iOS + Android + Windows，三端同服

- **结论**：首发 iOS、Android、Windows PC，三端玩家在同一个匹配池。
- **理由**：8 人对局需要足够大的匹配池；定点数核心保证 ARM64（手机）与 x64（PC、服务端）的战斗结果逐位一致，三端同服在技术上没有障碍。
- **影响**：
  - 美术与性能预算按移动端最低档制定，PC 只提高画质档位（04、08）。
  - 三端统一用 IL2CPP + HybridCLR；iOS 的代码热更合规处理见 07 §8。
  - 黄金回放测试要在 iOS、Android、Windows 真机上各跑一遍，与服务端哈希一致。
  - UI 同时支持触屏和鼠标：PC 的悬停提示在手机上对应长按；适配手机、iPad、PC 三种屏幕比例。
  - PC 首发 Steam。
  - iOS 构建与测试走 GitHub Actions（macOS runner → TestFlight），沿用 funny 的流水线，不需要本地 Mac（09）。
  - 待定：PC 玩家准备阶段操作更快，是否影响排位公平，原型阶段观察。

## ADR-010 · 2026-10-07 · Battle.Core 编进 AOT 壳，不走热更

- **结论**：`Automatic.Battle.Core` 移出热更列表，随安装包 IL2CPP 原生编译。热更层只剩 `Automatic.Game`（以及以后的演出、玩法内容程序集）。改了 ADR-008 中「Battle.Core 放在热更层」一条。
- **理由**：
  - 实测（10 §2）HybridCLR 社区版解释器比原生慢 12 倍。召唤流 300 单位一场在 PC 上 2.8 秒，A16 推算约 10 秒，观战快进和发热都不可接受；原生 PC 上 0.23 秒。
  - 同一份 Core 在 .NET、IL2CPP 原生、解释器下终局哈希逐位一致，换执行方式不影响确定性。
  - 商业版 DHE（没改动的函数跑原生，改动的函数解释执行）能保留 Core 的代码热更，但没有试用、要询价购买。DHE 要求的代码结构和本方案相同（Core 原生编译进壳），以后买了只换插件和打包配置，代码不用动。
- **影响**：
  - 改 Core 代码要发新壳（商店审核）。构建热更时会比对 Core 源码和上次打壳时的哈希，不一致就拒绝发布（`ShellCore`，07 §4）。
  - 平时的数值、战法调整不能写在 Core 里：Core 只放规则引擎和数据类型，具体的战法、牌型、数值放在单独的热更程序集或资源里（03 §7）。
  - 壳的 `link.xml` 整体保留 Core（只有热更代码调用它，不保留会被裁掉）；Core 加入补充元数据列表，热更代码可以实例化它的泛型。
  - 老壳的玩家靠 `EngineVersion` 校验强制更新（07 §5）。
  - 上线前再评估旗舰版 DHE：如果 Core 的紧急修复频繁到等不了商店审核，就购买。
