# 07 · 客户端热更方案

> 决策：ADR-008；Battle.Core 编进壳见 ADR-010。状态：草案，Unity 工程建好后先做最小验证（§7）。

## 1. 选型

| 层 | 方案 | 备选 / 不选的原因 |
|---|---|---|
| 代码 | **HybridCLR** | xLua / ILRuntime：要维护第二套语言或绑定层，Battle.Core 没法原样复用 |
| 资源 | **YooAsset** | Addressables：官方方案，但远程增量更新的流程较繁琐，版本管理不如 YooAsset 直观 |

热更 DLL 打成资源（`.bytes`），和美术资源走**同一份版本清单、同一个下载流程**。只有一套版本号，不会出现「代码新、资源旧」的错配。

## 2. 分层

```
AOT 壳（随安装包发布，尽量少改）
  ├─ 启动场景 + 启动界面（含下载进度、错误提示）
  ├─ 版本检查、YooAsset 下载、补充元数据加载
  ├─ 第三方原生插件、SDK
  ├─ Automatic.Battle.Core     确定性战斗核心（与服务端共享源码），IL2CPP 原生编译（ADR-010）
  └─ 入口：Assembly.Load(热更 DLL) → 反射调用 GameEntry.Start()

热更层（全部可以热更）
  ├─ Automatic.Game            对局流程、网络、商店、牌型 UI
  ├─ Automatic.Presentation    演出：事件流 → 动画 / 特效 / 镜头
  └─ 全部美术资源、配置数据、场景（启动场景除外）
```

规则：
- AOT 壳**不能引用**任何热更程序集（编译期由 asmdef 依赖关系保证）。
- 热更层的 MonoBehaviour 只挂在**通过 YooAsset 加载**的 prefab / 场景上，不放进安装包内的场景。
- Core 在壳里，只能随大版本更新。战法、牌型、数值这些数据**不写在 Core 里**，放在热更程序集或资源里（03 §7），平时的调整仍然只发热更。
- 热更代码可以调用 Core，Core 不能引用任何热更程序集。

## 3. 启动更新流程

```
启动 → 请求版本服（壳版本、平台）
     → 壳版本低于最低要求？ ── 是 → 提示去商店更新（大版本）
     → 下载远程清单，与本地缓存比对
     → 下载差异包（显示大小，移动网络下先询问）
     → 校验 → 加载补充元数据 → 加载热更 DLL → 进入游戏
```

- 版本服返回：最新资源版本、最低壳版本、CDN 地址。可以按渠道、灰度比例返回不同版本。
- 下载失败可以重试，并支持断点续传；校验失败就删掉缓存重新下载。
- 回滚：版本服把「最新版本」指回旧清单即可，CDN 上的旧版本文件保留。

### 出错处理（2026-10-07 Windows 实测）

YooAsset 的默认设置有两处会卡死玩家，原来的壳也没有重试。用故意出错的本地 CDN（`tools/hotupdate/`）逐项测过，改动在 `ResourceUpdater` 和 `Boot` 里，属于壳的改动：

| 情况 | 改之前 | 现在 |
|---|---|---|
| CDN 连不上 | 约 2 秒后显示失败，停在那里，只能重启游戏 | 自动重试，间隔 3、5、10、20、30 秒（之后每 30 秒一次），同时有「立即重试」按钮；CDN 一恢复就继续 |
| 下载中途断网，十几秒内恢复 | YooAsset 每个文件自动重试 3 次（间隔 1、2、3 秒），能撑过去 | 不变 |
| 断网更久 | 3 次重试用完后报失败，停住；重启后已下完的文件保留，没下完的从头下 | 外层继续重试；1 MB 以上的文件按字节续传（从断点接着下） |
| 服务器卡住，连接不断但不再发数据 | **永远卡在「下载中」**：YooAsset 对文件下载不设超时 | 15 秒收不到新数据就中断，从断点续传 |
| 本地缓存文件损坏 | **发现不了**：启动时只检查文件在不在。实测贴图包坏了，所有狰变成黑色剪影，没有任何提示，每次启动都一样 | 启动时用 CRC 校验全部缓存，坏的文件删掉，在同一次启动里重新下载 |

- 缓存位置也改了：YooAsset 在 Windows 上默认把缓存放在 exe 旁边（`Relics_Data/yoo`），装在 Program Files 下就写不进去。现在所有平台都放在 `Application.persistentDataPath/yoo`。
- CRC 校验的代价：PC 上 223 MB 缓存用了 0.4 秒。手机会慢几倍，上真机时要量；如果太慢，改成只校验大小，再加一个「修复客户端」（清缓存）按钮。
- 续传要求 CDN 支持 Range 请求，正式 CDN 都支持。本地的 `python -m http.server` 不支持，测续传要用 `tools/hotupdate/faulty_cdn.py`。
- CDN 不可用时，即使本地缓存完整也不会进游戏：对局需要连服务器，离线进游戏没有意义。
- 同样的代码编两次，生成的 DLL 不完全相同，所以回滚代码时 DLL 包（约 1.1 MB）还是要重下，回滚美术资源则不用。

## 4. 什么必须走大版本（换安装包）

- 修改 Battle.Core 的代码（ADR-010）。构建热更时 `ShellCore` 会对比 `src/Battle.Core` 源码和上次打壳时记下的哈希，不一致就拒绝发布：否则热更代码以为 Core 改了，实际跑的还是壳里的旧版。
- 升级 Unity 版本、HybridCLR 版本
- 新增或修改原生插件、SDK
- 热更代码用到了 AOT 中**没有实例化过的泛型**，而补充元数据也无法解决的情况（HybridCLR 文档里的 AOT 泛型限制）
- 修改启动场景、AOT 壳逻辑

应对：壳里预先引用常用的泛型组合（`List<FP>`、`Dictionary<int, T>` 等）；每次出大版本都审查一遍 AOT 泛型清单。

- **热更代码用到了壳里被裁掉的引擎 API**（2026-10-07 实测踩到）。
  - IL2CPP 打壳时会裁掉没人引用的引擎代码。HybridCLR 生成的 link.xml 只保留打壳那一刻热更 dll 引用到的部分。
  - 战斗切片的热更代码第一次调用 `MaterialPropertyBlock.SetColor`，旧壳里没有这个方法，运行时报 `MissingMethodException`。
  - 应对：`client/Assets/Boot/link.xml` 整体保留热更代码可能用到的引擎模块，包括 Core、Animation、ParticleSystem、Physics、Audio、UI、TextRendering 和 InputLegacy。
  - 代价：Windows 包的 `GameAssembly.dll` 从 45.1 MB 增加到 50.7 MB（+5.6 MB）。手机包的增量还要实测。
  - 以后热更代码要用这些模块之外的引擎模块（如 AI、Video），要先在壳里加上，否则只能等下一个壳。
  - 2026-10-07 加了 AndroidJNI 模块，用于在安卓上读启动参数和设备温度。注意它是内置包（`com.unity.modules.androidjni`），项目没启用时热更代码连编译都过不了，要先在 `Packages/manifest.json` 里启用。
  - 同一天又踩到 .NET 基础库的同类问题：召唤物压力测试用了 `System.Random.NextDouble`，壳里的 mscorlib 已经裁掉了它。基础库太大，不能整体保留。
  - **现在构建热更包时会自动检查**（`HotUpdateBuild.CheckShellApi`）：
    - 用 HybridCLR 的 `MissingMetadataChecker`，把热更 dll 引用的每个类型、方法、字段，和上次打壳裁剪后的 AOT dll 对一遍。
    - 有缺的就报出具体是哪个方法，并拒绝发布。
    - 检查器自带的版本漏查了全部基础库引用：Unity 编译的热更 dll 经由 netstandard 门面引用基础库，而它找不到这个门面，也不会加载门面转发到的 mscorlib。已补上门面，并预先加载基础库，修完后只报出 `NextDouble` 这一处真实问题。
    - 前提：本机最后一次打的壳就是 CDN 上那个壳。以后改成 CI 打包时，要把每个已发布壳的裁剪后 AOT dll 存档，按目标壳检查。

## 5. 与确定性战斗核心的关系（本项目特有）

Battle.Core 随壳发布（ADR-010），战斗数据随热更发布，老壳和旧数据的玩家都可能与服务端不一致，必须明确处理：

1. 壳记录 `EngineVersion`，每个热更版本记录数据哈希。客户端登录时上报这两个值。
2. **匹配前强制一致**：版本不一致就要求先更新，再进入匹配。同一局的 8 个人必须用同一版核心。
3. 服务端可以同时部署多个 `EngineVersion` 的对局服（灰度期间新旧并存），匹配按版本分组。
4. 战斗结果始终以服务端为准（01 §6），所以即使有漏网的版本不一致，也只是本地演出与结果对不上，不会造成判定错误。哈希不一致时上报，用来发现这类问题。
5. 对局进行中**不允许**热更，下载只在大厅进行。

## 6. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 解释执行性能 | HybridCLR 热更代码走解释器，比 AOT 慢 | 关键是观战时的无演出快进（01 §4）。在目标设备上实测，目标是 30 秒战斗在 100 毫秒以内快进完；不达标再考虑把 Core 移回 AOT（代价：Core 改动要走大版本）。**2026-10-07 实测**：解释器比 IL2CPP 原生慢 12 倍，召唤流 300 单位一场在 PC 上要 2.8 秒（A16 推算约 10 秒），不达标。已把 Core 移进壳（ADR-010），见 10 §4 |
| 确定性 | 解释器与 AOT 的整数运算结果必须一致 | 黄金回放测试同时在服务端（.NET）、编辑器、真机上跑，哈希一致。Core 编进壳后不再走解释器，但以后用 DHE 时改过的函数会解释执行，2026-10-07 已验证两者逐位一致 |
| Unity 升级 | HybridCLR 对新版本的支持有滞后 | 锁定 Unity 小版本，升级前确认 |
| iOS 合规 | App Store 审核指南 2.5.2 限制下载会改变功能的代码 | 见 §8 |
| Unity CoreCLR 迁移 | Unity 计划在桌面端引入 CoreCLR | 关注 HybridCLR 的跟进情况；移动端仍是 IL2CPP |

## 7. 最小验证（Unity 工程建好后第一件事）

1. 空工程接入 HybridCLR + YooAsset，打一个 Windows 包（或安卓包）。
2. 热更层里放一个 Cube 和一段 `FP` 运算，显示结果。
3. 修改代码和 Cube 的材质，只发布热更，不重装：重启后看到变化。
4. 在真机热更模式下跑 Prng 和 FP 的黄金值测试，结果和 `dotnet test` 一致。
5. 测一次 Battle.Core 快进性能。2026-10-07 用压测原型测过，见 10。

美术流程验证（08）的产出也要走一次这条热更链路。2026-10-07 已走通（材质、UI 文案、特效），见 08 §4。

**打包规则**：`Assets/HotRes` 按目录打包，但每个目录的材质和贴图各自单独成包（`<目录>_materials`、`<目录>_textures`），依赖方向是模型 / 预制体 / 场景 → 材质 → 贴图。调材质参数这种最常见的美术热更只下几 KB（08 §4）。

**2026-10-06 Windows 验证通过（第 1–4 步）**：Unity 6000.3.25f1 + HybridCLR 8.15.0 + YooAsset 3.0.6，IL2CPP 打包。exe 启动后从本地 CDN 拉资源，热更层里 7 项 Prng / FP 黄金值全部 PASS，与 `dotnet test` 一致。之后只发布热更（不重打 exe），重启后下载 2 个文件（约 1 MB），新代码文字和新材质颜色都生效。安卓、iOS 真机待做；第 5 步等 Core 有战斗逻辑后再补。

操作步骤见 `client/README.md`，全部步骤都能用 Unity CLI 无界面执行（`Assets/Editor/Batch.cs`）。本地用 `artifacts/cdn` 加 `python -m http.server` 充当 CDN；发布时先传包、最后传 `.version`，版本不比线上新就拒绝（09 §3 的护栏在本地先实现一遍）。

## 8. 三端差异（ADR-009）

| 项 | iOS | Android | Windows |
|---|---|---|---|
| 脚本后端 | IL2CPP（强制） | IL2CPP | **也用 IL2CPP**：三端走同一条热更路径，测试只覆盖一种 |
| 代码热更 | 有合规风险（下文） | 无限制 | 无限制（Steam 也允许） |
| 首包体积 | 蜂窝网络下载有大小提示 | Google Play 基础包有体积上限 | 无硬限制 |
| 构建 | GitHub Actions macOS runner（09） | CI ubuntu | CI windows |

### iOS 代码热更的处理

- 审核指南 2.5.2 不允许下载「引入或改变功能」的代码。行业通行做法是热更只用于修 bug、调数值、上新内容，不在热更里加新玩法系统。
- 版本服按平台下发开关 `codeHotUpdateEnabled`：iOS 出现审核问题时，可以单独关掉代码热更、只保留资源热更，其他平台不受影响。
- 新玩法系统跟随商店版本发布；热更 DLL 的变更记录要能说明每次改了什么。

### 首包

- 安装包里只放 AOT 壳、启动界面和新手第一局需要的资源，其余由 YooAsset 首次启动时下载。
- 下载前显示大小，蜂窝网络下先询问。

### 构建

- 不需要本地 Mac：iOS 走 GitHub Actions 的 macOS runner，构建后上传 TestFlight，详见 09。
