# 07 · 客户端热更方案

> 决策：ADR-008。状态：草案，Unity 工程建好后先做最小验证（§7）。

## 1. 选型

| 层 | 方案 | 备选 / 不选的原因 |
|---|---|---|
| 代码 | **HybridCLR** | xLua / ILRuntime：要维护第二套语言或绑定层，Battle.Core 没法原样复用 |
| 资源 | **YooAsset** | Addressables：官方方案，但远程增量更新的流程较繁琐，版本管理不如 YooAsset 直观 |

热更 DLL 打成资源（`.bytes`），和美术资源走**同一份版本清单、同一个下载流程**。只有一套版本号，不会出现「代码新、资源旧」的错配。

## 2. 分层

```
AOT 壳（随安装包发布，尽量少改）
  ├─ 启动场景 + 启动界面（含下载进度、错误提示）
  ├─ 版本检查、YooAsset 下载、补充元数据加载
  ├─ 第三方原生插件、SDK
  └─ 入口：Assembly.Load(热更 DLL) → 反射调用 GameEntry.Start()

热更层（全部可以热更）
  ├─ Automatic.Battle.Core     确定性战斗核心（与服务端共享源码）
  ├─ Automatic.Game            对局流程、网络、商店、牌型 UI
  ├─ Automatic.Presentation    演出：事件流 → 动画 / 特效 / 镜头
  └─ 全部美术资源、配置数据、场景（启动场景除外）
```

规则：
- AOT 壳**不能引用**任何热更程序集（编译期由 asmdef 依赖关系保证）。
- 热更层的 MonoBehaviour 只挂在**通过 YooAsset 加载**的 prefab / 场景上，不放进安装包内的场景。
- 战法、牌型、数值这些数据写在 Core 的 C# 记录里（03 §7），跟着 DLL 一起热更，不需要单独的表格热更通道。

## 3. 启动更新流程

```
启动 → 请求版本服（壳版本、平台）
     → 壳版本低于最低要求？ ── 是 → 提示去商店更新（大版本）
     → 下载远程清单，与本地缓存比对
     → 下载差异包（显示大小，移动网络下先询问）
     → 校验 → 加载补充元数据 → 加载热更 DLL → 进入游戏
```

- 版本服返回：最新资源版本、最低壳版本、CDN 地址。可以按渠道、灰度比例返回不同版本。
- 下载失败可以重试，并支持断点续传；校验失败就删掉缓存重新下载。
- 回滚：版本服把「最新版本」指回旧清单即可，CDN 上的旧版本文件保留。

## 4. 什么必须走大版本（换安装包）

- 升级 Unity 版本、HybridCLR 版本
- 新增或修改原生插件、SDK
- 热更代码用到了 AOT 中**没有实例化过的泛型**，而补充元数据也无法解决的情况（HybridCLR 文档里的 AOT 泛型限制）
- 修改启动场景、AOT 壳逻辑

应对：壳里预先引用常用的泛型组合（`List<FP>`、`Dictionary<int, T>` 等）；每次出大版本都审查一遍 AOT 泛型清单。

## 5. 与确定性战斗核心的关系（本项目特有）

Battle.Core 在热更层，所以**客户端与服务端的核心版本可能不一致**，必须明确处理：

1. 每个热更版本记录 `EngineVersion` 和数据哈希。客户端登录时上报这两个值。
2. **匹配前强制一致**：版本不一致就要求先更新，再进入匹配。同一局的 8 个人必须用同一版核心。
3. 服务端可以同时部署多个 `EngineVersion` 的对局服（灰度期间新旧并存），匹配按版本分组。
4. 战斗结果始终以服务端为准（01 §6），所以即使有漏网的版本不一致，也只是本地演出与结果对不上，不会造成判定错误。哈希不一致时上报，用来发现这类问题。
5. 对局进行中**不允许**热更，下载只在大厅进行。

## 6. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 解释执行性能 | HybridCLR 热更代码走解释器，比 AOT 慢 | 关键是观战时的无演出快进（01 §4）。在目标设备上实测，目标是 30 秒战斗在 100 毫秒以内快进完；不达标再考虑把 Core 移回 AOT（代价：Core 改动要走大版本） |
| 确定性 | 解释器与 AOT 的整数运算结果必须一致 | 黄金回放测试同时在服务端（.NET）、编辑器、真机热更模式下跑，三边哈希一致 |
| Unity 升级 | HybridCLR 对新版本的支持有滞后 | 锁定 Unity 小版本，升级前确认 |
| iOS 合规 | App Store 审核指南 2.5.2 限制下载会改变功能的代码 | 见 §8 |
| Unity CoreCLR 迁移 | Unity 计划在桌面端引入 CoreCLR | 关注 HybridCLR 的跟进情况；移动端仍是 IL2CPP |

## 7. 最小验证（Unity 工程建好后第一件事）

1. 空工程接入 HybridCLR + YooAsset，打一个 Windows 包（或安卓包）。
2. 热更层里放一个 Cube 和一段 `FP` 运算，显示结果。
3. 修改代码和 Cube 的材质，只发布热更，不重装：重启后看到变化。
4. 在真机热更模式下跑 Prng 和 FP 的黄金值测试，结果和 `dotnet test` 一致。
5. 测一次 Battle.Core 快进性能（Core 有战斗逻辑之后再补）。

美术流程验证（08）的产出也要走一次这条热更链路。

## 8. 三端差异（ADR-009）

| 项 | iOS | Android | Windows |
|---|---|---|---|
| 脚本后端 | IL2CPP（强制） | IL2CPP | **也用 IL2CPP**：三端走同一条热更路径，测试只覆盖一种 |
| 代码热更 | 有合规风险（下文） | 无限制 | 无限制（Steam 也允许） |
| 首包体积 | 蜂窝网络下载有大小提示 | Google Play 基础包有体积上限 | 无硬限制 |
| 构建 | GitHub Actions macOS runner（09） | CI ubuntu | CI windows |

### iOS 代码热更的处理

- 审核指南 2.5.2 不允许下载「引入或改变功能」的代码。行业通行做法是热更只用于修 bug、调数值、上新内容，不在热更里加新玩法系统。
- 版本服按平台下发开关 `codeHotUpdateEnabled`：iOS 出现审核问题时，可以单独关掉代码热更、只保留资源热更，其他平台不受影响。
- 新玩法系统跟随商店版本发布；热更 DLL 的变更记录要能说明每次改了什么。

### 首包

- 安装包里只放 AOT 壳、启动界面和新手第一局需要的资源，其余由 YooAsset 首次启动时下载。
- 下载前显示大小，蜂窝网络下先询问。

### 构建

- 不需要本地 Mac：iOS 走 GitHub Actions 的 macOS runner，构建后上传 TestFlight，详见 09。
