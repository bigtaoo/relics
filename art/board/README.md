# 棋盘场景验证（08 §2）

生成：`unity run client -- -executeMethod Automatic.Editor.Batch.BoardSlice`

- 脚本：`client/Assets/Editor/BoardSlice.cs` 负责单位、镜头、截图和统计，`BoardDressing.cs` 负责棋盘、地貌、灯光和后处理。所有贴图和网格都由脚本生成，重跑时原地覆盖，GUID 不变。
- 场景：`client/Assets/HotRes/Scenes/board_west.unity`，在热更资源目录里。场景单独放一个目录，因为 YooAsset 不能把场景和普通资源打进同一个包。
- 截图：`phone_19.5x9.png`、`pad_4x3.png`、`pc_16x9.png`，三种比例都用同一个战斗镜头（俯角 50°，FOV 30），镜头自动拉远到整张桌面都能放进画面。

## 2026-10-06 第 1 版

**布局（临时）**：每方 3 排 × 5 列，中间一条「河」（象棋棋盘的做法），每方再加 8 格备战席。三演的真实行列数还没截图确认（02 §3），这些数字都是 `BoardLayout` 里的常量，确认后改常量就行。

**画面**：
- 桌面做成「山海舆图」：一张生成的纸面贴图，墨线画格子，己方半场冷色、敌方半场暖色，格子棋盘格交错。
- 地面是带等高线的旧地图，西山用红岩低多边形山。
- 后处理：泛光、饱和度和对比度调整、暗角。

**单位**：
- 46 只狰，两边的格子和备战席全部放满（最坏情况）。档位随机，偏向低档。
- 敌我靠两样区分：底座颜色（蓝 / 红）和血条颜色（绿 / 红）。
- 正在行动的单位：活体态，摆攻击姿势，脚下有一个发光金环。

**可读性结论**：
- 敌我：清楚。
- 谁在行动：金环能看出来，但不够醒目，正式版还要配合镜头或特效。
- 单位要侧转 40° 朝向对面。正对或背对镜头时，四足兽从俯视角看只是一团，侧过来才看得出身体轮廓。
- 青铜、玉、金：能分开。
- **陶和活体态撞色**：都是橙红色加深色斑点，行动单位只能靠金环认出来。陶也和敌方的红色底座混在一起。建议把陶改成灰陶或白陶。还有一个设计问题要先定：战斗中单位是否都「活过来」？如果是，战斗中就看不出档位了。
- **手机 19.5:9 下单位偏小**：整张桌面（含两边备战席）都要放进画面，高度决定了缩放，左右两边空出很多。需要决定手机上的取景：裁掉对方备战席，或者镜头推近、允许拖动。

**性能（静态数据）**：
- 单位：46 个蒙皮网格，**88.3 万三角面**（单只 1.92 万面，Tripo 输出原样），1794 根骨骼。
- 场景其余部分：166 个静态渲染器、5.8 千三角面。材质 16 个。
- 编辑器里在这台 PC 上渲染约 4–5 ms/帧，**这不是设备数据**。
- 结论：单只面数要降到约 3–5 千（移动端满场 15–25 万面），这一步要先做减面或 LOD 再上真机。描边是第二遍绘制，等于每只单位的顶点再处理一遍，算预算时要算进去。
- 真机帧率还没测：需要把场景接进热更入口，打包到基准机型上跑。

### 材质单独打包（同日）

打包规则从 `PackDirectory` 换成自定义的 `PackDirectoryMaterialsApart`（`client/Assets/Editor/MaterialPackRule.cs`）：仍按目录打包，但每个目录里的 `.mat` 单独成一个 `<目录>_materials` 包，贴图单独成一个 `<目录>_textures` 包。

- 只拆材质时，特效目录会出现循环依赖：预制体引用材质，材质又引用同目录的贴图。所以贴图也一起拆，依赖变成单向的：模型、预制体、场景 → 材质 → 贴图。
- 狰的 1.7 MB 拆成：模型和动作 285 KB、贴图 1458 KB、材质 3 KB。棋盘、特效、UI 也一样拆开。

## 2026-10-07 内存和合批（08 §4 性能）

`-bench` 加了两样东西：内存计数器，以及渲染计数器的逐帧记录（报中位数）。单帧读数会跳，有的帧只报三分之一的三角面。10-06 那次只取了最后一帧，碰巧是正常值。另外加了两个开关：`-nosrpbatch` 关掉 SRP Batcher，`-nooutline` 关掉描边。都是 1920×1080 窗口，开发本，各跑两次。

| 状态 | 平均帧时间 | SetPass | draw call | 三角面 |
|---|---|---|---|---|
| 修之前 | 3.1–3.9 ms | 234（关掉 SRP Batcher：237） | 444 | 43 万 |
| 修之前，关掉描边（诊断用） | 2.5 ms | 5（关掉 SRP Batcher：21） | 329 | 29 万 |
| 修之后 | 2.1–2.3 ms | **6**（关掉 SRP Batcher：35） | 442 | 43 万 |

- **原因**：描边是 `Relics/Toon` 里的第二个 pass（LightMode `SRPDefaultUnlit`）。URP 在同一次绘制里逐个物体画「正常着色 → 描边」，着色器每次都切换，所以 SRP Batcher 开不开都一样。
- **修法**：描边 pass 改用自定义的 LightMode `Outline`，由 URP 渲染器里的 RenderObjects 特性「Toon Outline」在不透明物体之后统一画（`ProjectSetup.EnsureOutlinePass`）。渲染器在安装包里，这是壳的改动：新着色器配旧壳会没有描边。
- 顺带把阴影和深度 pass 从 `UsePass "Universal Render Pipeline/Lit/..."` 改成自己写的。借来的 pass 用的是 Lit 的材质参数布局，按 Unity 的规则会让整个着色器不兼容 SRP Batcher。单独改这一项时 SetPass 没变（还是 234），主因是描边。
- 修完后画面不变：同一时间点的截图差异 3–5.6% 像素，和同样内容跑两次的差异一样（来自待机动画相位）。放大看描边粗细相同。
- draw call 没变（442）：SRP Batcher 降低的是每次绘制的状态切换开销，不减少 draw call 数。估算来源：46 只单位和 46 个底座各画正常着色和描边，再加血条，以及 119 个投影物体的阴影。没有逐项核对。

**内存**（开发版，修之后，1080p）：

| 项 | MB |
|---|---|
| 进程总占用（System Used，含驱动和开发版开销） | 约 720 |
| Unity 已用（Total Used） | 约 330 |
| 其中显存（Gfx Used，含 1080p 的渲染目标和阴影贴图） | 约 190 |
| 其中贴图 | 40 |
| 其中网格 | 0.5（蒙皮网格的数据在显存里） |
| 托管堆（GC Used） | 约 8 |

- 包是开发版（Development Build），会多出 profiler 等开销。发布版和手机上的数字要在真机测试时重量。
- 手机分辨率更低，渲染目标会小很多。贴图 40 MB 由哪些贴图组成还没拆开看。

## 2026-10-07 同屏 300 单位 + 特效（召唤流压力测试）

召唤流可能同屏约 300 个单位，召唤物可以用低模。在满场 46 只狰（每只 3000 面）的基础上，再加 254 只低模召唤物，合计 300。召唤物是同一只狰，每只 400 面，用 `tools/art/blender/lowpoly.py` 减面，骨骼和动作不变。召唤物按 0.5 倍大小撒满两边半场，每 1.5–3.5 秒攻击一次，头顶都有血条。截图 `crowd_vat.jpg`、`crowd_fx120.jpg`（120 个特效同时播放）。

召唤物试了两种画法：

- **蒙皮**：和棋子一样，每只一个 Animator 加蒙皮网格。
- **顶点动画贴图（VAT）**：编辑器把每个动作逐帧烘焙进两张贴图（`Batch.CrowdBake`），里面存的是每个顶点在每一帧的位置和法线。运行时没有 Animator 也没有蒙皮，着色器按动作和时间直接读出顶点，所有召唤物用 GPU 实例化一次画完（`Relics/Toon` 的 `_VAT` 开关）。每只召唤物只需要传位置、朝向和当前动作。

全部是 1920×1080 窗口，开发本（Core Ultra 7 165H 加 Intel Arc 核显），开发版。

| 场景 | 平均帧时间 | 主线程 | GPU | draw call | SetPass | Unity 已用内存 |
|---|---|---|---|---|---|---|
| 只有 46 只棋子 | 1.57 ms | 0.90 ms | 1.38 ms | 441 | 7 | 300 MB |
| + 254 召唤物，蒙皮 | 3.81 ms | 2.69 ms | 2.40 ms | 1192 | 13 | 441 MB |
| + 254 召唤物，蒙皮，去掉骨骼节点（`-optimize`） | 3.97 ms | 2.68 ms | 2.54 ms | 1195 | 13 | — |
| + 254 召唤物，VAT | **2.20 ms** | 1.62 ms | 1.86 ms | **451** | 17 | **338 MB** |
| + 454 召唤物（共 500），VAT，60 个特效 | 2.36 ms | 1.81 ms | 2.07 ms | 514 | 81 | — |

- **300 单位在 PC 上没有问题**，蒙皮也能跑到 260 fps。但 PC 不能代表手机：手机的 CPU 单核大约慢 3–4 倍，GPU 要慢一个数量级以上。
- **召唤物应该用 VAT**：
  - 比蒙皮省掉了 1.1 ms 主线程（Animator 和 CPU 蒙皮），draw call 从 1192 降到 451。
  - 内存少约 100 MB：每个蒙皮实例都有自己的一份蒙皮后网格和 Animator 数据。
  - 加到 500 只，帧时间也只多一点点。
  - 在手机上，这几项正是瓶颈所在。
- **VAT 的限制**：
  - 动作只能整段播放，不能混合过渡，也不能挂武器、按骨骼挂特效。
  - 贴图大小随顶点数 × 总帧数增长：这只召唤物 605 顶点 × 174 帧 = 1.6 MB。
  - 棋子本身（数量少、要混合和挂点）继续用蒙皮。
- **骨骼节点优化**（`AnimatorUtility.OptimizeTransformHierarchy`）在 PC 上没有收益，瓶颈不在骨骼节点。手机上要重测。
- **CPU 蒙皮还是 GPU 蒙皮**：上面几行都是在 CPU 蒙皮的壳上测的（当时项目设置是 `meshDeformation: 0`）。2026-10-07 在 PC 上补测了 GPU 蒙皮（batched），见下一节。
- **特效**：数据见 `art/fx/README.md` §5。表里最后一行 SetPass 81 是特效材质交错造成的，已改成图集加一个材质，现在特效多时 SetPass 在 20 多（同节「图集」）。

**复现方法**：先开本地 CDN，然后运行：

```
Relics.exe -bench -crowd 254 -vat -fx 60 -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 -logFile bench.log
```

参数说明：
- 不加 `-vat` 就是蒙皮画法。
- `-optimize` 去掉蒙皮召唤物的骨骼节点。
- `-shot <目录>` 在预热后存一张截图。

## 2026-10-07 CPU 蒙皮 vs GPU 蒙皮（PC）

蒙皮方式是壳的设置（`PlayerSettings.meshDeformation`），所以两种各打一个 Windows 包，用同一套参数测，其他条件和上一节相同。两次测试时机器负载比上一节略高，所以 CPU 蒙皮这列数字整体偏高一点，只在同一列内比较。

| 场景 | CPU 蒙皮 | GPU 蒙皮（batched） |
|---|---|---|
| 只有 46 只棋子 | 2.00 ms（主线程 1.13，GPU 1.41） | 1.83 ms（主线程 1.08，GPU 1.27） |
| + 254 召唤物，蒙皮 | 4.92 ms（主线程 3.11，GPU 3.11） | **3.95 ms**（主线程 3.16，GPU 2.11） |
| + 254 召唤物，VAT | 2.42 ms | 2.50 ms |

- GPU 蒙皮在 300 只蒙皮单位时快了约 1 ms，主要省在 GPU 时间上：CPU 蒙皮每帧要把蒙皮后的顶点重新传给显卡。
- 主线程没有变化，约 3.1 ms。蒙皮单位的主线程开销在 Animator，不在蒙皮。所以召唤物还是要用 VAT。
- VAT 不受影响，因为它本来就不走蒙皮。
- 已把壳改成 GPU 蒙皮（batched），写进 `ProjectSetup`。A16 的 GPU 很弱，手机上的结论可能相反，要在真机上再对比一次：打一个 CPU 蒙皮的包跑同样的测试。
